The premise

A type system should remember what a value means.

Ostrin is for software where a wrong value can be more dangerous than a wrong number. The language makes the domain visible before the program runs.

01

Dimensions are types

Lengths, times and derived quantities are checked before execution. A meter is not just a number with a comment beside it.

5 m + 2 s → error
02

Mutation is visible

Values are immutable by default. When state changes, the binding says so. Sharing and concurrency start from an explicit baseline.

mut counter = 0
03

Errors have a shape

Option, Result and exhaustive match keep failure states in the model instead of hiding them in control flow.

try parse(input)

Explore the language

Small decisions. Large consequences.

The core is deliberately compact. Its power comes from making a few important rules compose cleanly.

01 / TYPES

Physical quantities

Write values such as 10 m and 2 s. Arithmetic preserves dimensions and rejects incompatible operations.

Quantity<Length / Time>
02 / FLOW

Readable control flow

Expressions, pattern matching, explicit try and readable boolean operators keep intent close to the code.

match result { ... }
03 / SCALE

Traits and modules

Traits, generics, records, enums and modules form a foundation for libraries that can grow with the language.

trait Printable { ... }

A working example

The compiler should catch the expensive mistake.

Ostrin is especially useful where values have meaning beyond their numeric representation: measurements, simulations, controls and domain models.

accepted / dimensional arithmetic

velocity = 10 m / 2 s

The compiler derives Quantity<Length / Time> and carries that information forward.

rejected / incompatible values

distance + duration

The operation fails before execution because the dimensions do not describe the same kind of value.
