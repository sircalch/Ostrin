`v0.2.0` tag, publishing a GitHub release, or changing installer channels.

## Before requesting publication authorization

1. Verify `main` is the reviewed merge commit, the PR commits are ancestors, and required
   CI, CodeQL, dependency audit, browser audit, native sanitizers, WASI, readiness,
   documentation and website checks pass.
2. Verify the 12 readiness criteria and all evidence links. Preserve open boundaries:
   this is experimental 0.x software; R3 remains open; Linguist recognition is not claimed;
   cross-platform numerical equivalence and universal memory safety are not claimed.
3. Run the release build workflow against the exact proposed commit **by SHA/ref that is
   not a tag** as a non-publishing rehearsal. The post-merge rehearsal at `aaa9f16` is
   recorded with separate hashes in the candidate manifest; those hashes are not final-tag
   hashes. The release workflow's `publish` job runs for
   any `refs/tags/v*`, including `workflow_dispatch` at a tag, so do not dispatch it from a
   tag for rehearsal. Save the rehearsal logs but do not treat its hashes as final tag hashes.
4. Confirm all three host archives pass target tests, compiler version and hello smoke,
   extraction, packaged project smoke, and SHA-256 sidecar verification. Confirm the WASI
   compiler and 28-program matrix, and verify every entry in its `SHA256SUMS`.
5. Confirm `docs/releases/v0.2.0.md` is written as final release notes, the changelog and
   compatibility notes match the source, installers still resolve the existing published
   release until publication, and the website labels 0.2.0 as unreleased while 0.1.0 remains
   latest.
6. Present the exact proposed commit, full check links, final notes, and the side effects of
   the tag-triggered publish workflow for explicit owner authorization.

## Authorized tag workflow: required checks

After separate explicit authorization only, create `v0.2.0` at the approved commit. The tag
push itself starts `.github/workflows/release.yml`, which tests/builds/packages Linux
x86_64, macOS ARM64, Windows x64 and WASI Preview 1, smoke-tests extracted archives, creates
and verifies SHA-256 sidecars and the WASI module manifest, then creates the GitHub release
with all four platform assets after the readiness gate. Capture the resulting workflow run
IDs, exact tag
object/peeled commit, archive names, real SHA-256 values, sidecar verification, extraction
and smoke outcomes in `validation/release-candidate-v0.2.0.json` as final-release evidence.
Those post-tag records are evidence of the tagged release and must not be represented as
RC hashes. Verify the release assets and public URLs from GitHub, then verify
`https://sircalch.github.io/Ostrin/`, status metadata, installer resolution and version
labels. The public site must show 0.2.0 as published only after the release exists.

## Installation and compatibility notes

When published, invoke the repository's `scripts/install.sh` with `sh` (Linux/macOS), or
use `scripts/install.ps1` (Windows) with explicit version `0.2.0`; verify the downloaded
archive against the attached `.sha256` file and run `ostrinc --version`,
`ostrinc --check examples/hello.ostrin`, and `ostrinc --run examples/hello.ostrin`.
WASI users should download the attached tagged release asset and verify both the archive
checksum and `SHA256SUMS` before running the Node WASI smoke. Supported release targets are Linux x86_64 glibc, macOS ARM64,
Windows x64, and WASI Preview 1. Linux ARM64, Intel macOS, musl and package-manager channels
are outside this release matrix. Ostrin is experimental and 0.x compatibility permits
syntax, diagnostic and API changes; do not describe this release as production-ready.

## Known limitations to carry into release notes

The interpreter remains the semantic reference, and native HIR/IR support is limited to
tested source shapes. `Measurement<Quantity<D>>`, `Array<Measurement<T>>`, broader nested
ownership combinations and general cancellation states remain guarded or unsupported.
R3 provenance is incomplete (29 bundles base-ready; 4,266 effect calls unresolved). General
cross-platform numerical equivalence, upstream GitHub Linguist recognition, and comparisons
against Python, Julia, MATLAB or Wolfram are not release claims.

## Rollback plan

If tag CI fails before creating a release, stop and diagnose; do not move or reuse the tag.
Correct the source or workflow through a reviewed commit and obtain approval for the exact
replacement tag target. If a release is partially created or an integrity/critical defect is
found after publication, preserve logs and downloaded hashes, announce the issue, and ask
the release owner to authorize unpublishing/removing assets or the release. Never silently
replace files under an existing version. For a shipped defect, prepare a corrected patch
release with fresh artifacts and checksums. Verify the installer points to the intended
version during rollback and return the website to the last verified published version.
